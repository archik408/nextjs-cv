## Строгость TypeScript (должно соответствовать политике проекта)

Используй строгие настройки, эквивалентные тем, что включены в `tsconfig.json`:

```json
"noImplicitAny": true,
"skipLibCheck": true,
"strict": true,
"noEmitOnError": true,
"noFallthroughCasesInSwitch": true,
"noImplicitOverride": true,
"noImplicitReturns": true,
"noUnusedLocals": true
```

Примечания:

- `skipLibCheck: true` разрешён для ускорения, но наши собственные типы должны быть корректными.
- Не отключай строгие правила через `// eslint-disable` / `// @ts-ignore` без очень веской причины и комментария, почему это безопасно.

## Стандарты тестирования

- Пиши тесты для сложной логики.
- Предпочитай:
  - модульные тесты для чистой/алгоритмической логики и не-React части,
  - интеграционные тесты для взаимодействий компонентов и границ потока данных,
  - сквозные (e2e) — только там, где это даёт уникальное покрытие.
- Следуй пирамиде тестирования и идее «трофей тестирования»:
  - много быстрых модульных тестов,
  - меньше интеграционных тестов,
  - минимально e2e.

## Технологический стек и архитектура, которые мы соблюдаем

- Next.js App Router + React (FC/hooks) + TypeScript (strict) + Tailwind CSS.
- По умолчанию компоненты серверные: это важно для производительности и SEO. `use client` используем только когда реально нужны state/effects/DOM.
- Языки (EN/RU) и переводы — централизованно через `LanguageProvider` и `translations.ts` (без параллельных источников правды).
- Тема (dark/light) — с одним источником правды через `ThemeProvider` и класс `dark` на `html/body`.
- SEO: контент должен быть индексируемым, с корректными metadata/structured data и стабильными URL.

## Правила из `.cursor/rules` (отдельными разделами)

### Базовые стандарты

- Основной стек: **Next.js App Router + React (FC/hooks) + TypeScript (strict) + Tailwind CSS**.
- Новые страницы и инструменты создаём в `app/` (segment layout, server components, streaming).
- По умолчанию компонент серверный; `use client` используем только при необходимости состояния, эффектов или доступа к DOM/Browser API.
- Бизнес‑логика, безопасность и утилиты живут в `lib/` (и `lib/hooks/` для `use-*`), UI‑слой — в `components/` с логичной структурой (sections/ui/icons и т.п.).
- Не создаём “god‑компоненты”: если компонент становится слишком большим/многоответственным — выносим части в подкомпоненты или хуки.

# TypeScript и чистота кода

- Строгая типизация: избегаем `any`; если он всё же нужен — строго локализуем и документируем причину.
- Общие типы и интерфейсы выносим в общие модули (`types/` или `lib/types/`) и переиспользуем.
- Порядок в файле: импорты → типы/константы → основной компонент → вспомогательные функции.
- Не отключаем ESLint/Prettier правила без понятного комментария (почему правило здесь неприменимо).
- Комментарии пишем на одном языке (предпочтительно английском), чтобы код оставался однородным.

# Переиспользование и структура JSX

- Повторяющиеся паттерны (контейнеры секций, разделители, карточки) выносим в отдельные компоненты (`<PageSection />`, `<SectionDivider />` и т.д.).
- Следим за семантикой: там, где можно использовать нативный элемент (`<button>`, `<a>`, `<section>`, `<header>`), используем его, а не `div + onClick`.
- Не дублируем сложную логику в нескольких местах; выделяем её в кастомные хуки (`use-*`) и чистые функции в `lib/`.

### Accessibility

- На каждой странице должен быть один `main` с ясной иерархией заголовков (`h1` → `h2` → `h3`).
- Skip‑link ведёт на начало основного контента (`#main-content`); при изменении структуры обязательно синхронизируем `href` и `id`.
- Первый видимый заголовок в main должен описывать основное содержание страницы (особенно для инструментов/страниц с одним core‑флоу).

# Клавиатура, фокус и интерактивность

- Любой интерактивный контрол (кнопка, ссылка, переключатель темы/языка, карточка-инструмент) доступен с клавиатуры и имеет чёткий фокус.
- Диалоги/модалки/лайтбоксы:
  - используют `use-focus-trap` для захвата фокуса,
  - фокус при открытии попадает внутрь диалога,
  - при закрытии возвращается на инициировавший элемент.
- Escape всегда закрывает активный диалог, не оставляя невидимых, но фокусируемых элементов.

# ARIA, роли и медиа

- Сначала используем нативные элементы и семантику; `role` и `aria-*` добавляем только для уточнения/исправления.
- Гарантируем, что `aria-labelledby` и `aria-describedby` указывают на реально существующие, стабильные DOM‑узлы.
- Значимые изображения имеют содержательное `alt`; декоративные — `alt=""` и по возможности `aria-hidden="true"`.

# Анимации и уменьшенная анимация

- Новые анимации/эффекты учитывают `prefers-reduced-motion`: при reduce‑настройке анимации не должны мешать использованию интерфейса.
- Длительные/броские анимации (hero, section title, Lottie и т.п.) должны иметь понятный статичный fallback.

# A11y‑тесты

- Для ключевых секций и страниц (hero, testimonials, tools, модалки, крупные инструменты) добавляем `jest-axe`‑проверки.
- При нахождении нарушений фиксируем код, а не отключаем правило без причины.

### Security

# Общие принципы

- Любые входные данные (query, body, headers, localStorage) считаем недоверенными и валидируем до использования.
- Не возвращаем во фронтенд внутренние stack trace или подробные сообщения об ошибках серверной логики/сторонних API.

# API-маршруты и middleware

- В `app/api/**/route.ts`:
  - валидируем и санитизируем входные данные (используем `lib/security.ts` и/или отдельные схемы),
  - явно ограничиваем и проверяем типы и формат (например, enum языков, whitelist для filename и т.п.),
  - возвращаем только необходимые данные и минимальную диагностическую информацию.
- Изменяя заголовки безопасности (CSP, HSTS, X-Frame-Options и др.) в `next.config.ts` или middleware, не ослабляем их без взвешенного решения и комментария.
- Rate limiting реализуем централизованно; не плодим разные частные реализации по файлам.

# Фронтенд‑безопасность

- `dangerouslySetInnerHTML` используем только для:
  - заранее подготовленного, доверенного HTML (например, markdown → HTML, контролируемого нами),
  - строго документированных интеграций (structured data, inline‑скрипты темы).
- Не вставляем в DOM сырые строки с потенциально опасным содержимым (HTML, JS, URLs) без санитизации.
- Любые чувствительные значения (ключи API, токены) никогда не попадают в клиентский бандл и не читаются из env‑переменных на клиенте.

# Внешние ресурсы

- При добавлении новых CDN/шрифтов/скриптов:
  - пересматриваем и дополняем CSP (sources‑списки),
  - проверяем, что это не даёт потенциального XSS/арбитрарного исполняемого кода.

### Интернационализация и тема

# Международизация (i18n)

- Пользовательские строки не хардкодим в компонентах; все тексты подключаем через `use-language` и структуру переводов (`translations.ts` и/или связанные модули).
- Для новой строки обязательно добавляем переводы `en` и `ru` или явно помечаем, что контент односторонний (например, только RU для Digital Garden).
- Переводы храним в структурированном виде (группы по страницам/фичам), избегаем “магических” ключей и копипаста.
- Текущий язык хранится и управляется через `LanguageProvider`; не создаём параллельные источники правды (локальный `useState` со своим языком).
- Атрибут `lang` на `<html>` должен отражать активный язык; при переключении языка корректно обновляем его.

# Тема (light/dark)

- Источник правды по теме — `ThemeProvider` и класс `dark` на `html/body` (плюс существующий inline‑скрипт в `<head>`); не вводим альтернативные механизмы.
- При добавлении новых компонентов:
  - всегда проверяем их внешний вид в светлой и тёмной теме,
  - используем `dark:`‑варианты классов Tailwind и/или переменные (`--background`, `--foreground`) там, где это уместно.
- Не ломаем текущую стратегию предотвращения FOUC/FOT (мигания темы): если меняем логику определения/применения темы, делаем это централизованно и совместимо с inline‑скриптом.

### Производительность

# Загрузка, ошибки и UX

- Для маршрутов с ожидаемой задержкой (загрузка данных, тяжёлые вычисления) добавляем `loading.tsx` с понятным скелетоном/фолбэком.
- Используем `error.tsx` на уровне приложения/сегментов, чтобы перехватывать ошибки рендера/данных и показывать дружелюбный recovery‑UI.
- Для 404‑сценариев используем `not-found.tsx` вместо “глухого” пустого состояния.

# Код-сплиттинг и dynamic imports

- Тяжёлые и неуниверсальные компоненты (Lottie, SVG/изображения‑оптимизаторы, OCR, AI‑инструменты и др.) подключаем через `next/dynamic`.
- При использовании `dynamic`:
  - по возможности задаём `loading`‑компонент/скелетон,
  - для строго клиентских модулей указываем `ssr: false`.
- Избегаем импортов больших модулей на страницы, где они фактически не нужны; следим за тем, чтобы главная и лёгкие страницы оставались быстрыми.

# Работа с ресурсами

- Для значимых изображений используем `next/image` с корректными `sizes` и конфигом `images` в `next.config.ts`.
- Следим за размером и форматом ассетов в `public/` (SVG, PNG, JPG); по возможности используем оптимизированные версии и кэширование.

# Микрооптимизации React

- При заметных перерендерах больших деревьев или списков:
  - используем `React.memo` и мемоизацию пропсов (через `useMemo`/`useCallback`) там, где это даёт реальный профит,
  - избегаем лишних анонимных функций/объектов в пропах горячих компонентов.
- Логику, зависящую от размера окна/скролла (анимации секций, эффекты при скролле) реализуем аккуратно:
  - используем `passive`‑слушатели и debounce/throttle при необходимости,
  - учитываем `prefers-reduced-motion`, чтобы не тратить ресурсы впустую.
